# VulBox — The Journey So Far

**Last updated:** 2026-05-17
**Companion to:** `docs/PROGRESS_REPORT.md` (long-form audit) and `README.md` (commands).
**Purpose:** one narrative pass over what we built, what we cut corners on, what we deliberately deferred, and what stands between today's prototype and a consumer-ready app.

---

## 1. What VulBox is (one paragraph)

An automated application-security assessment pipeline. A user submits a Git repo; VulBox clones and Docker-builds it, scans the resulting image with Trivy, deploys it to an isolated sandbox under Falco runtime monitoring, fires Atomic Red Team techniques at it, and emits a three-dimensional **Security Matrix** — *Is the vulnerability present? Is it exploitable? Is it detectable?* — plus an LLM-generated remediation for each row. The whole pipeline is exposed via FastAPI + a WebSocket event stream and rendered in an eight-screen React dashboard.

## 2. Where we are vs. where we started

| Phase | Then (Apr 2026 baseline) | Now (May 2026) |
|---|---|---|
| Data model | Flat `Finding` table conflating three concepts | Seven SDD-aligned tables: `AssessmentRun`, `TrivyFinding`, `ARTTestResult`, `FalcoAlert`, `SecurityMatrixEntry`, `Remediation`, `User` |
| Orchestration | None — endpoints did the work inline | Async state machine with self-healing rebuild loop, 1800 s timeout, max 3 rebuilds, try/finally cleanup |
| CVE → Technique map | 55 hand-curated CVEs / 12 techniques | **1,465 unique CVEs** (55 curated + 2,017 generated, merged), **1,060 KEV-flagged**, 7 signal-driven fallback rules |
| ART techniques | 13 hand-written bash bodies | 17 techniques with **88 vendored Linux atomic tests** from the upstream Atomic Red Team repo (pinned SHA `37400ed6`) |
| Tests | ~10 fixture parsers | **69 passing** across parsers, correlation, remediation, CVE-map, LLM mocks, ART catalog, ground-truth-static |
| Frontend | 4 screens, basic forms | 8 screens with sidebar nav, phase-stepper, coloured risk-chip matrix, PDF/CSV export |
| Auth | None | JWT scaffolding wired in (login/register/me) — **not yet enforced on data routes** |
| Validation | None | Ground-truth harness (`scripts/validate_e2e.py`) + manifest of 3 control images; demo runbook + reset script |

The trajectory is roughly: **"vertical slice working end-to-end on fixtures" → "data spine wide enough to cover real CVEs and real techniques" → (next) "trustworthy enough for someone outside the team to run."**

## 3. The fallbacks we live with today

Every one of these is a deliberate choice — usually "ship a demo path, document the caveat." None are bugs; all are debt.

### 3.1 Dev mode vs. production mode

The three adapters (`TrivyAdapter`, `FalcoAdapter`, `ARTAdapter`) branch on `VULBOX_DEV_MODE`. In **dev mode** they read from `data/sample_outputs/*.json` fixture files; in production they shell out to `trivy`, `falco`, and `scanners/atomic_runner.{py,sh}`. The dev path has been exercised hundreds of times. The production path has been *implemented but never end-to-end-verified in CI*. Everything we ship in test reports describes the dev path unless explicitly noted otherwise.

### 3.2 LLM remediation → static-rule fallback

`app/services/llm_remediation.py` calls OpenAI with prompt-cache-friendly inputs and parses JSON with markdown-fence stripping. If the API key is missing, the flag is off, the call errors, JSON parsing fails, or required fields are missing, it falls back to one of **four static rules** keyed only on `(exploited, detectable)`. That fallback ships a coherent remediation — but every Critical finding gets the same text. The LLM path itself has never been validated against a golden-set; we know it produces *plausible* output, not that it produces *useful* output.

### 3.3 PDF export → 501

`/reports/{id}/export?format=pdf` uses `weasyprint`. If `weasyprint` (and its `libpango`/`libcairo` system deps) is missing, the endpoint returns HTTP 501. The frontend's "Export PDF" button has no handling for this — it opens a new tab on the 501 page. JSON and CSV exports work unconditionally.

### 3.4 ART tests with no Linux atomic

The new `scanners/atomic_runner.py` picks a vendored atomic when one exists. For techniques the upstream catalog doesn't cover under Linux (container-escape edge cases, the systemd-write variant, our hand-written probes), it delegates back to `scanners/atomic_runner.sh`. Both layers honour the `ATOMIC_CONSENT=true` gate.

### 3.5 SQLite + `create_all`

No Alembic. Schema changes are "delete `data/findings.db` and start fresh." Adequate for a prototype where every run is throw-away. Unworkable the moment a real user has a report they care about preserving.

### 3.6 Ground-truth validation report

`docs/validation_report.md` exists and is auto-generated by `scripts/validate_e2e.py`. The static-coverage and atomic-catalog sections are populated. The **"Ground-truth E2E corpus" section still says "No results yet"** because the harness needs a host with Docker + Trivy and we have not yet run it there. The infrastructure is ready; the run hasn't happened.

### 3.7 Falco subprocesses

`falco_adapter.py` stores per-run `Popen` handles in a module-level dict. If the API process dies between `attach()` and `collect_alerts()`, the Falco process can orphan. Nothing reaps it on next API start. On a long-running deployment this leaks privileged processes; on a demo VM it's invisible.

### 3.8 Hardcoded frontend API URL

`frontend/src/api.js` and `frontend/src/pages/Report.jsx` both hardcode `http://46.101.193.155:8000`. Every frontend build is coupled to that one VM. The fix (a single `VITE_API_BASE_URL` env var) is one of the smallest items on the roadmap and one of the most embarrassing to still have open.

## 4. Missing features — the gap to consumer-ready

Ordered roughly by how badly they block external use.

### 4.1 Auth enforcement on the data plane (blocker)

`get_current_user` is a `Depends` import that today lives only in `app/api/auth.py`. The other twelve routes — `GET /runs`, `GET /runs/{id}`, `GET /runs/{id}/validations`, every `/reports/*` endpoint, every `/runs/{id}/ingest/*` endpoint, and the `/ws/runs/{id}/status` WebSocket — accept any caller. The frontend Reports page calls `GET /runs` without scoping, so any logged-in user sees every run from every other user. Any unauthenticated caller on the same network sees the same thing.

### 4.2 User scoping on data (blocker)

`AssessmentRun` has no `user_id` foreign key. There is no concept of "my runs." Fixing 4.1 without also adding `user_id` and `.filter(...)` on every query gets you a UI that just says "Forbidden" everywhere. They must ship together.

### 4.3 Per-app run configuration (blocker for false-positive rate)

Today a run is configured by `project_name`, `repo_url`, `branch`, `image_tag`, and a consent checkbox. There is no `.vulbox.yml`-style mechanism to:
- Skip techniques that don't apply.
- Whitelist sensitive paths the app legitimately reads (so Falco doesn't false-positive).
- Allow specific egress destinations (today the sandbox is `--network none`).
- Provide build args / build secrets (private package registries are unbuildable).
- Set resource limits or per-technique time budgets.

On a real Flask or Spring Boot app, the matrix will fill with "detectable findings" that are actually normal startup behaviour. The user has no way to silence them.

### 4.4 Real-target proof (credibility blocker)

The orchestrator has never been verified against an arbitrary GitHub repository. The ground-truth corpus (`tests/ground_truth/manifest.yml`) lists three control images (`alpine:3.20`, `alpine:3.5`, `debian:8`); the harness is written; the execution is pending. Until `docs/validation_report.md` shows green diffs against expected findings on at least these three images, we can't credibly claim "VulBox runs end-to-end."

### 4.5 Failure transparency

`AssessmentRun` has no `error_message` column. When the orchestrator transitions to `FAILED`, the frontend shows "Assessment failed during the BUILDING phase. Check server logs for details." Troubleshooting requires SSH access to the API host. This makes the product unsupportable.

### 4.6 LLM remediation quality

Today's remediations are plausible-looking. We have no harness that asks "would an engineer paste this into a PR?" The doc-level gap: no golden-set of `(evidence, expected remediation)` pairs; no precision/recall scoring; no prompt iteration loop; no "low-confidence — defer to human" branch.

### 4.7 Schema migrations

No Alembic. Any schema change wipes every existing run, report, and user. Required before any external user holds onto a report for longer than a session.

### 4.8 Observability

Structured logs exist (`app/core/logging.py`); metrics and tracing don't. There is no `runs_total`, `run_duration_seconds`, `llm_call_failures_total`. Debugging a slow or stuck pipeline today means reading log lines.

### 4.9 Data retention and audit

Reports, run records, ART results, and Falco alerts accumulate indefinitely. No archival, no deletion, no anonymisation. No audit log of who created what, deleted what, or exported what. For a security tool, these are compliance basics.

### 4.10 Concurrency

SQLite serialises writes with file-level locking. Fine for one demo user, painful for multi-tenant. Postgres migration is on the long-term list.

## 5. Improvements we shipped (and why they mattered)

A short list of things that turned out to be more impactful than expected.

| Improvement | Why it mattered |
|---|---|
| **Async state machine with try/finally cleanup** | Made the pipeline observable and the failure modes legible. Before this every error was a 500 with no audit trail. |
| **WebSocket replay buffer (200 events)** | The biggest single quality-of-life win for the demo. A user joining the status page late still sees the full history of their run. |
| **CVE → MITRE map expansion** (55 → 1,465) | Moved the map from "toy" to "actually useful." KEV flagging gave us a real prioritisation signal. |
| **Vendoring the Atomic Red Team catalog at a pinned SHA** | Replaced 13 hand-written bash bodies with 88 community-maintained tests. We stopped owning that code. |
| **Ground-truth manifest format** | Forced us to write down *what we expect each target to produce* — that artifact, more than the harness itself, is what makes future regressions catchable. |
| **Three-dimensional Security Matrix in the report UI** | The coloured-chip matrix made `present / exploitable / detectable` legible without reading any prose. It's the screenshot the project gets judged by. |
| **`docs/DEMO_RUNBOOK.md`** | T-24h / T-1h / T-0 checklist + a documented fallback path to dev mode when full mode breaks live. Took the panic out of demos. |
| **`is_blocking() == False` on `TrivyAdapter`** | Implements SDD §4.12.2: scan findings never stop the pipeline. Sounds small; it's the rule that makes "Phase 1 result feeds Phase 3 prioritisation" possible. |

## 6. What we'd do differently

- **Build auth in from the start.** Adding `Depends(get_current_user)` to twelve routes after the fact is one task; doing it as each route was written would have been zero tasks.
- **Pick a Postgres-first stance earlier.** SQLite was great for the first ten weeks and is now a foregone migration cost.
- **Treat the validation report as a first-class output.** It currently lives in `docs/` next to design docs; it should be linked from the dashboard and refreshed by CI on every merge.
- **Pin every external image digest in `docker-compose.yml` and CI.** Right now a `node:18-alpine` upstream change can silently move our finding counts.
- **Write the LLM golden-set before the LLM service.** We have evaluation infrastructure ready for the static rules and the parser, and zero infrastructure for evaluating the actual output quality of the thing we want users to read.

## 7. The shortest credible path to "consumer-ready"

Roughly two months of focused work, in the order that buys the most credibility per week:

1. **Week 1–2 — close the auth gap.** `get_current_user` on every route, `user_id` FK on `AssessmentRun`, runtime consent re-check at the top of `_phase_test_loop`, `error_message` column with frontend surfacing, `VITE_API_BASE_URL`, Alembic initialised with one migration.
2. **Week 3–5 — prove the end-to-end claim.** Run `scripts/validate_e2e.py` on a Docker-enabled CI runner; get green diffs on the three control images; extend the corpus to five (a Flask app, a Node Express, a Spring Boot, a Go binary, Juice Shop). Publish `docs/PERFORMANCE.md` with measured wall-clock and resource budgets.
3. **Week 6–8 — make the report worth reading.** Build the 15-case LLM golden-set; iterate prompt to ≥ 70% "would-act-on-it" rate; add the low-confidence path that flags entries for human review.
4. **Week 9–12 — per-app config + technique parallelism.** Land `.vulbox.yml` v1, add the "Configure run" step in the frontend, parallelise independent ART techniques in the orchestrator.

Sprint 5 (audit log, quotas, Postgres, metrics) is the long tail and runs in parallel from week 6.

---

## 8. Honest one-line status

> **VulBox is a working proof-of-concept that demonstrates the SDD's three-dimensional Security Matrix is a viable architecture, with a wide enough data spine to cover real CVEs and real techniques. The security and configurability work that lets someone outside the team trust it on an unfamiliar repository has not been started.**

That is the gap between today and consumer-ready. Everything in §4 is what closes it.
